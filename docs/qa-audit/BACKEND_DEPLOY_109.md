# Backend 1.0.9: procedimiento del operador

Preparado el 7-oct-2026. Este documento y el script no ejecutan producción por sí solos. Root informó que las migraciones 0063, 0064 y 0065 ya se aplicaron con exit 0; comprobar ese estado antes de continuar.

1. Revisar cambios y ejecutar `node scripts/deploy-backend-109.mjs`. Es un plan local sin red. Requiere CLI local 2.114.0 y obtiene el proyecto de EXPO_PUBLIC_SUPABASE_URL. No imprime credenciales.
2. Antes del despliegue, comprobar por Management API solamente nombres/presencia de REVENUECAT_API_KEY y RITUAL_SECRET. La presencia o un hash opaco no demuestran que la clave RevenueCat sea válida ni que RITUAL_SECRET coincida con Vault. El operador debe disponer de una clave servidor RevenueCat válida y confirmar la correspondencia del secreto existente por un canal protegido, sin copiarlo a mensajes o logs.
3. Solo Root: `node scripts/deploy-backend-109.mjs --apply`. readToken suministra SUPABASE_ACCESS_TOKEN al entorno del proceso hijo; no existe flag --token. Despliega secuencialmente mediante --use-api: coach, account-erasure, store-reconcile con JWT habilitado; revenuecat-webhook y store-erasure-cleanup con --no-verify-jwt. El worker autentica x-ritual-secret dentro del handler. El script verifica ACTIVE, incremento de versión y verify_jwt tras cada función. Ante fallo se detiene; los despliegues anteriores pueden haber tenido efecto. No modifica secretos ni cron.
4. Comprobar Vault por consultas protegidas: nombres nivl_ritual_secret y nivl_project_url presentes y no vacíos; URL coincide exactamente con el proyecto destino. No devolver decrypted_secret ni registrar cabeceras. La coincidencia de nombres entre Vault y Edge no demuestra igualdad de valores.
5. Antes de activar cron, Root debe probar una petición protegida al worker usando el secreto desde Vault, con pg_net o un proceso que mantenga la credencial solo en memoria. Esta petición puede drenar hasta 20 borrados pendientes: es una acción de producción, no un preflight de lectura. Verificar HTTP 200 y campos ok/processed/pending, sin imprimir cuerpos que puedan incluir información ajena. Si devuelve 401, no activar cron: revisar gateway verify_jwt=false y correspondencia RITUAL_SECRET/Vault. Si devuelve 503, revisar configuración RevenueCat/RPC y cola antes de continuar. No probar con un UUID en el cuerpo: el worker usa exclusivamente los leases de la cola.
6. Revisar `node scripts/setup-store-erasure-cleanup.mjs` (imprime SQL). Solo tras la comprobación anterior, Root puede ejecutar `node scripts/setup-store-erasure-cleanup.mjs --apply`. El script usa las referencias Vault existentes y habilita nivl-store-erasure-cleanup con frecuencia de 15 minutos. No crea secretos nuevos.
7. Verificar mediante lectura cron.job, cron.job_run_details y respuestas pg_net: trabajo activo, destino correcto y respuestas autenticadas satisfactorias. No publicar payloads, cabeceras, UUID ni tokens de lease. Mantener seguimiento de pendientes/fallos mediante contadores agregados.

Los 15 minutos son frecuencia del scheduler y próxima elegibilidad después de un DELETE satisfactorio; no garantizan un DELETE por cuenta cada 15 minutos. El worker procesa lotes de 20 y el backlog puede retrasar el drenado. La ventana persistente de 30 días y leases de 5 minutos permiten repetir borrados y recuperar ejecuciones interrumpidas; no constituyen una garantía ilimitada frente a un GET remoto arbitrariamente tardío.

Validación local del procedimiento: node --check del script y modo PLAN satisfactorios. No se ejecutó --apply, petición al worker, cambios de secretos ni activación del scheduler desde este agente. Este procedimiento no cubre Simulator/TestFlight ni implica aprobación de tienda.
